## 🔄 Взаимодействие компонентов

### 1. Поток данных от Google Sheets до Frontend

```
Google Sheets → Backend → PostgreSQL → Redis → Frontend
      │            │          │           │        │
      ▼            ▼          ▼           ▼        ▼
   Источник   Обработка   Хранение    Кеширование  Отображение
   данных     и валидация            для быстрого
                                   доступа
```

**Детальный процесс:**
1. **Google Sheets API** → Backend (каждые 10 минут)
   - Загрузка данных через сервисный аккаунт
   - Парсинг таблиц в структурированные записи

2. **Backend Processing** → PostgreSQL
   - Валидация данных по схеме из `datasets.json`
   - Дедупликация (3 стратегии)
   - Спам-фильтрация (keywords + regex)
   - Сохранение в PostgreSQL

3. **API Requests** ←→ Redis ←→ PostgreSQL
   - Запросы от Frontend кешируются в Redis
   - Часто запрашиваемые данные (статистика, первые страницы) в кеше
   - Редкие запросы идут напрямую к PostgreSQL

4. **Frontend** ← Backend API
   - React приложение запрашивает данные через API
   - Пагинация, сортировка, фильтрация на стороне backend
   - Lazy loading для больших таблиц

### 2. Роль каждого компонента

#### **Frontend (React)**
- **Назначение**: Пользовательский интерфейс
- **Технологии**: React 18, TypeScript, TanStack Query, Tailwind CSS
- **Функции**:
  - Отображение данных в таблицах с пагинацией
  - Поиск и фильтрация
  - Визуализация отчетов
  - Адаптивный дизайн

#### **Backend (FastAPI)**
- **Назначение**: Обработка данных и API
- **Технологии**: FastAPI, SQLAlchemy, Pydantic
- **Модули**:
  - `data_loader.py`: Загрузка из Google Sheets
  - `deduplicator.py`: Дедупликация записей
  - `spam_filter.py`: Фильтрация спама
  - `validator.py`: Валидация данных
  - API endpoints: `/api/v1/data/*`, `/api/v1/ingest/*`

#### **PostgreSQL**
- **Назначение**: Основное хранилище данных
- **Структура**:
  - Таблица `records`: Все загруженные записи
  - JSONB поле `data`: Гибкое хранение структурированных данных
  - Индексы: full-text search, bloom filters, composite indexes

#### **Redis**
- **Назначение**: Кеширование для производительности
- **Использование**:
  - Кеш статистики (TTL: 5 минут)
  - Кеш часто запрашиваемых записей
  - Bloom filters для быстрой проверки дубликатов
  - Сессии пользователей (если будет авторизация)

#### **Nginx**
- **Назначение**: Reverse proxy и балансировка нагрузки
- **Функции**:
  - Маршрутизация запросов к нужным сервисам
  - SSL/TLS termination
  - Rate limiting
  - Gzip compression

#### **Apache Superset**
- **Назначение**: Продвинутая аналитика и отчеты
- **Интеграция**:
  - Подключается к PostgreSQL как источник данных
  - Создание дашбордов и визуализаций
  - Scheduled reports и алерты
  - Доступ через `/superset/` путь

### 3. Поток запросов от пользователя

```
Пользователь → Frontend → Nginx → Backend → [Redis → PostgreSQL]
      │           │          │        │          │         │
      ▼           ▼          ▼        ▼          ▼         ▼
   Запрос   HTTP запрос  Маршрутизация  Обработка  Кеш   База данных
   данных                и балансировка  API       проверка
```

**Пример: Просмотр таблицы с обращениями**
1. Пользователь открывает `/data` в браузере
2. Frontend отправляет запрос: `GET /api/v1/data/community_requests?page=1&per_page=50`
3. Nginx перенаправляет запрос на backend
4. Backend проверяет кеш Redis для этой страницы
5. Если нет в кеше → запрос к PostgreSQL с пагинацией
6. Данные кешируются в Redis (TTL: 1 минута)
7. Ответ возвращается через цепочку обратно к пользователю

### 4. Синхронизация с Google Sheets

```
Scheduler → Data Loader → Processing Pipeline → PostgreSQL
    │           │               │                   │
    ▼           ▼               ▼                   ▼
 Каждые    Загрузка     Валидация →          Сохранение
 10 мин   данных из    Дедупликация →        обновленных
         Google Sheets Спам-фильтрация       записей
```

**Процесс синхронизации:**
1. **Планировщик (APScheduler)** запускает задачу каждые 10 минут
2. **Data Loader** подключается к Google Sheets API
3. **Processing Pipeline**:
   - Парсинг сырых данных в структурированные записи
   - Валидация по схеме из `datasets.json`
   - Проверка дубликатов (3 стратегии)
   - Фильтрация спама
   - Расчет хешей для будущей дедупликации
4. **Сохранение** в PostgreSQL с метаданными

### 5. Дедупликация (3 стратегии)

```
Новая запись → [Стратегия 1] → [Стратегия 2] → [Стратегия 3] → Сохранение
                   │               │               │
                   ▼               ▼               ▼
             По source_id    По хешу полей   Bloom filter
```

**Стратегии:**
1. **По source_id**: Если запись с таким source_id уже существует
2. **По хешу уникальных полей**: MD5 хеш от `тема` + `от_кого` + `дата`
3. **Bloom filter**: Вероятностная структура для быстрой проверки

### 6. Спам-фильтрация (3 уровня)

```
Новая запись → [Уровень 1] → [Уровень 2] → [Уровень 3] → Классификация
                   │             │             │
                   ▼             ▼             ▼
             Keywords       Regex patterns  ML-ready
             (спам, реклама) (URLs, CAPS)   (расширяемо)
```

### 7. Кеширование в Redis

```
Запрос данных → Redis Cache → [HIT] → Возврат из кеша
       │            │
       ▼            ▼
   [MISS] → PostgreSQL → Сохранение в кеш → Возврат данных
```

**Кешируемые данные:**
- **Статистика**: `stats:{dataset_id}:exclude_spam:{bool}` (TTL: 5 мин)
- **Записи**: `record:{dataset_id}:{record_id}` (TTL: 10 мин)
- **Страницы**: `page:{dataset_id}:{page}:{per_page}:{filters}` (TTL: 1 мин)
- **Bloom filters**: `bloom:{dataset_id}` (постоянно)

### 8. Пагинация и Lazy Loading

```
Frontend Table → API Request → Backend Pagination → Response
      │               │               │                 │
      ▼               ▼               ▼                 ▼
  Показ 50   Запрос страницы  LIMIT/OFFSET  50 записей +
 записей     с параметрами    запрос к БД   метаданные
                              (оптимизированный)
```

**Backend Pagination:**
```sql
-- Пример запроса для страницы 2 (50 записей на странице)
SELECT * FROM records 
WHERE dataset_id = 'community_requests' 
ORDER BY created_at DESC 
LIMIT 50 OFFSET 50;
```

### 9. Интеграция с Superset

```
Superset → PostgreSQL Connection → Data Exploration → Dashboards
    │           │                       │                 │
    ▼           ▼                       ▼                 ▼
Веб-интерфейс  Прямое    Анализ через   Публикация
аналитики   подключение   SQL и визуализации  дашбордов
             к БД
```

**Преимущества:**
- Мощная аналитика без написания кода
- Scheduled reports и email рассылки
- Продвинутые визуализации (графики, карты, heatmaps)
- SQL Lab для сложных запросов

## 🔧 Конфигурация взаимодействия

### Docker Compose сеть
```yaml
networks:
  udds-network:
    driver: bridge
```

Все сервисы находятся в одной сети `udds-network` и общаются по именам:
- `backend` → `postgres:5432`
- `backend` → `redis:6379`
- `frontend` → `backend:8000` (через Nginx)
- `superset` → `postgres:5432`
- `nginx` → `frontend:80` и `backend:8000`

### Health Checks
Каждый сервис имеет health checks для мониторинга:
- **PostgreSQL**: `pg_isready -U udds -d udds`
- **Redis**: `redis-cli ping`
- **Backend**: `curl -f http://localhost:8000/api/v1/health`
- **Frontend**: `wget --spider http://localhost:80/`

## 🚀 Масштабирование

### Вертикальное масштабирование
1. **Увеличение ресурсов**:
   - PostgreSQL: больше RAM для кеша запросов
   - Redis: больше памяти для кеша
   - Backend: больше CPU для параллельной обработки

2. **Оптимизация запросов**:
   - Индексы в PostgreSQL
   - Query optimization
   - Materialized views для часто запрашиваемых данных

### Горизонтальное масштабирование
1. **Backend реплики**:
   - Несколько инстансов backend за балансировщиком
   - Stateless архитектура (сессии в Redis)

2. **Чтение/запись разделение**:
   - PostgreSQL read replicas для отчетов
   - Primary для записи, replicas для чтения

3. **Кеширование**:
   - Redis cluster для распределенного кеша
   - CDN для статических файлов frontend

## 🔒 Безопасность взаимодействия

1. **CORS**: Настроены только разрешенные origins
2. **Rate Limiting**: Ограничение запросов через Nginx
3. **API Validation**: Валидация всех входных данных
4. **SQL Injection Protection**: Использование ORM (SQLAlchemy)
5. **Secrets Management**: Переменные окружения, не в коде

Эта архитектура обеспечивает надежную, масштабируемую и производительную систему для работы с данными из Google Sheets.
